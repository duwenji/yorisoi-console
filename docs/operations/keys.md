# 鍵の手順書

ルート鍵と署名鍵を作る・保管する・入れ替える・失効させる手順（[ARCH-001](../architecture.md) A-8・A-9、[platform API-CHANNEL-LIST](https://github.com/duwenji/yorisoi-platform/blob/main/docs/contracts/API-CHANNEL-LIST.md) P-1・P-2）。画面の操作は[運営ガイド 5 章](../guide/operator.md#5-署名鍵と鍵セット)、KMS の鍵の追加は[保守ガイド 8 章](../guide/maintainer.md#8-署名鍵を足す)にあり、この手順書はそれらをいつ・どの順で使うかと、画面の外で行うことを書く。

## 1. 鍵と置き場所

| もの | 置き場所 | 秘密か | 失ったとき |
|---|---|---|---|
| ルート鍵の秘密鍵（`root-key.pem`、合言葉で暗号化） | USB メモリ 2 本（別々の場所）。ネットにつながる端末には置かない | 秘密 | 鍵セットを作れない（[7 章](#7-ルート鍵をなくした漏れた)） |
| ルート鍵の合言葉 | 紙 1 枚。USB メモリとは別の場所 | 秘密 | 同上 |
| ルート鍵の公開鍵（`root-key.pub`）とリストID | [配備の手順](deploy.md)の表、CDK の `rootPublicKey`、アプリの内蔵のリスト | 公開してよい | 公開鍵は秘密鍵から作り直せる |
| 署名鍵 | KMS（取り出せない。ARCH-001 A-8） | KMS の外に出ない | 新しい鍵を作って入れ替える（[5 章](#5-署名鍵を入れ替える半年ごと)） |
| 鍵セット（ルート鍵の署名つき） | 管理システムの `KEYSET`、案内文書 | 公開される | 運営の画面の履歴に残る |

担当: ルート鍵と USB メモリ・紙は**運営**が持つ。KMS の鍵を作るのは**開発・保守の担当者**。1 人が両方を兼ねてもよい。

開発用のリストは別のルート鍵を持ち、扱いはゆるい（[配備の手順](deploy.md#開発用dev)。秘密鍵と合言葉をホームのフォルダに置き、`tools/provision` で署名する）。この手順書は**本番**の手順。本番では `tools/provision` を使わない（ルート鍵をネットにつながる端末に置くことになるため。`--env prod` は拒む）。

## 2. オフラインの端末を用意する

ルート鍵を使うのは、ネットにつながない端末だけにする。

- 専用のノート PC、またはネットにつないでいない PC を USB メモリの Linux（Ubuntu のライブ USB など）で起動したもの
- Wi-Fi と Bluetooth を切り、LAN ケーブルを抜く
- Node.js 22 以上と、このリポジトリを `npm ci` した状態のものを入れる。ネットにつながる端末で用意して USB メモリで写す（`node_modules` ごと）。使うのは `tools/root-key` と `packages/protocol` だけ
- オフラインの端末に写すのはルート鍵の CLI と、署名する入力（`keyset-input.json`）だけ。持ち出すのは署名した鍵セット（`keyset.json`）と公開鍵だけ

合言葉はコマンドの行に書かず、画面に出さずに入れる（シェルの履歴に残さないため）。

```sh
read -rs ROOT_KEY_PASSPHRASE && export ROOT_KEY_PASSPHRASE
```

## 3. ルート鍵を作る（本番で 1 回）

1. 合言葉を決める（16 文字以上。パスワード生成器で作る）。紙に書く
2. オフラインの端末で作る。出力先は 1 本目の USB メモリ

   ```sh
   read -rs ROOT_KEY_PASSPHRASE && export ROOT_KEY_PASSPHRASE
   npm run root-key -w tools/root-key -- generate --out /media/usb1/yorisoi-prod
   ```

   画面に `provider:`（リストID）と `rootKey:`（公開鍵）が出る。同じ値が `root-key.pub` にもある。すでに `root-key.pem` があるフォルダには作らない（上書きを拒む）
3. `yorisoi-prod` のフォルダを 2 本目の USB メモリに写す
4. 2 本目から読めることを確かめる: [4 章](#4-最初の鍵セット本番の最初の配備)の最初の鍵セットに、1 本目と 2 本目の両方で署名し、どちらも `verify-keyset` が `ok` になること
5. `root-key.pub` だけを運営の端末に写し、リストIDと公開鍵を[配備の手順](deploy.md)の本番の表に書く（プルリクエスト）
6. USB メモリ 2 本と紙を、別々の場所にしまう（自宅の金庫と貸金庫など。火事や盗難で同時に失わない場所）

## 4. 最初の鍵セット（本番の最初の配備）

本番の配備は、ルート鍵・独自ドメイン（ARCH-001 未決事項 No.1）・SES（No.6）がそろってから。

1. 開発・保守の担当者が配備する（[配備の手順](deploy.md)の本番。`-c env=prod -c rootPublicKey=<rootKey>`）。署名鍵 `signingKeyIds` の最初の鍵ができる。出力の `SigningKeyArn0` を運営に渡す
2. 運営が画面で KMS の鍵を登録する（[運営ガイド 5.3](../guide/operator.md#53-署名鍵の入れ替え半年ごと) の 2）
3. その鍵にチェックを入れ、有効期間を **270 日**にして鍵セットの入力を作る（[運営ガイド 5.2](../guide/operator.md#52-鍵セットを登録する)）。270 日は、半年ごとの入れ替えが遅れても 3 か月の余裕を残すため（上限は 366 日）
4. オフラインの端末で署名し、`verify-keyset` で確かめてから持ち出す

   ```sh
   npm run root-key -w tools/root-key -- sign-keyset --root-key /media/usb1/yorisoi-prod/root-key.pem --in /media/transfer/keyset-input.json --out /media/transfer/keyset.json
   npm run root-key -w tools/root-key -- verify-keyset --in /media/transfer/keyset.json --root-public-key <rootKey> --provider <リストID>
   ```

   `/media/transfer` は運営の端末との受け渡しに使う USB メモリ（ルート鍵の写しとは別）。CLI は `tools/root-key` のフォルダで動くので、ファイルは絶対パスで書く

5. 画面で登録する。リストが作り直される
6. 準拠テストを流す（[配備の手順](deploy.md)の 3）
7. アプリの内蔵のリスト（platform stakeholders W-1）に、リストID・ルート鍵の公開鍵・公開 URL を入れる。ルート鍵を入れ替えるとアプリの更新が要るので、内蔵するのはここで作ったルート鍵だけ

## 5. 署名鍵を入れ替える（半年ごと）

4 月と 10 月に入れ替える。鍵 ID は `k-<年>-<月>`（例 `k-2027-04`）。

| 段 | だれが | すること |
|---|---|---|
| 1 | 開発・保守 | 新しい KMS の鍵を作り、ARN を渡す（[保守ガイド 8](../guide/maintainer.md#8-署名鍵を足す)） |
| 2 | 運営 | 画面で登録し、新旧の両方を載せた鍵セット（有効期間 270 日）にオフラインで署名して登録する（[運営ガイド 5.3](../guide/operator.md#53-署名鍵の入れ替え半年ごと) の 2・3） |
| 3 | 運営 | 1 日以上たってから、新しい鍵だけの鍵セットに署名して登録する（同 4）。アプリが前の鍵セットを持っていても、取得のたびに新しい鍵セットが届く |
| 4 | 開発・保守 | 古い鍵の有効期間が過ぎたら、KMS で古い鍵の削除を予約する（[保守ガイド 8](../guide/maintainer.md#8-署名鍵を足す) の最後） |

同じ日に、ルート鍵の 2 本の写しの両方で署名できることを確かめる（段 2 の署名を 2 本で行う）。読めない写しがあれば、読める写しから作り直す。

入れ替えを忘れると、鍵の有効期間が切れたところでリストに署名できなくなり、リストの期限（概要の警告）が近づく。予定表に 4 月と 10 月の作業を入れておく。

## 6. 署名鍵を失効させる（漏れた疑い）

署名鍵が使われた疑い（管理システムの乗っ取り、身に覚えのない公開の履歴、AWS の認証情報の漏えい）があるときは、その日のうちに行う（[運営ガイド 11 章](../guide/operator.md#11-緊急時の対応)）。

1. 開発・保守の担当者が新しい KMS の鍵を作る（[5 章](#5-署名鍵を入れ替える半年ごと)の段 1）。乗っ取りの疑いなら、先に AWS の認証情報と運営のアカウントを入れ替える
2. 運営が新しい鍵を登録し、新しい鍵だけを載せ、疑わしい鍵 ID を `revokedKeys` に足した鍵セットにオフラインで署名して登録する（[運営ガイド 5.4](../guide/operator.md#54-署名鍵を失効させる)）
3. 公開の履歴を見て、疑わしい鍵で署名された覚えのない公開がないか確かめる

アプリには最大 24 時間（取得の間隔）で届き、失効した鍵で署名されたリストは署名の日時にかかわらず使われなくなる（platform API-CHANNEL-LIST）。

## 7. ルート鍵をなくした・漏れた

ルート鍵は管理システムの外で立て直す手段なので、これを失うとアプリの更新が要る（platform API-CHANNEL-LIST の「ルート鍵の入れ替えはリストIDが変わる」）。

| 事態 | 影響 | すること |
|---|---|---|
| 写しの 1 本が読めない・なくした | なし（もう 1 本がある） | 読める写しから 2 本目を作り直す。なくした USB メモリが第三者に渡った恐れがあれば、下の「秘密鍵だけ漏れた」も行う |
| 写しが 2 本とも使えない | 鍵セットを作れない。今の署名鍵は有効期間の間だけ使える | [3 章](#3-ルート鍵を作る本番で-1-回)で新しいルート鍵を作り、そのリストIDのリストを用意し（`rootPublicKey` を変えて配備する。今のチャンネルなどのデータを引き継ぐ方法は、そのときに開発・保守の担当者が確かめる）、アプリの更新で内蔵のリストを差し替える。今の署名鍵が切れるまで（最長 270 日）にアプリを出す |
| 秘密鍵だけ漏れた（合言葉は漏れていない） | すぐには使えない（AES-256 で暗号化。合言葉は 16 文字以上） | 合言葉を知られていない間に、上と同じ手順で新しいリストへ移る。急がないが、次のアプリの更新までに |
| 秘密鍵と合言葉の両方が漏れた | 第三者が鍵セットを作り、自分の署名鍵を載せて偽のリストを出せる（ただし偽のリストを置ける公開 URL が要る） | 直ちに新しいリストへ移り、アプリの更新を急いで出す。更新しない端末は古いリストを信じ続けるので、ストアの説明と通知で更新を呼びかける |

## 8. 記録

- 画面での登録は操作の記録（`signing-key.register`・`keyset.register`）に残る
- オフラインの端末での操作（日付、何をしたか、鍵セットの `seq`、どの写しを使ったか）は、USB メモリと一緒にしまうノートに書く
