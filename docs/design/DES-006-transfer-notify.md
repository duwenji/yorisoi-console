# DES-006 鍵の移し替えとチャンネル提供者へのメール

## 文書情報

| 項目 | 内容 |
|---|---|
| 文書ID | DES-006 |
| ドキュメント種別 | 機能設計書 |
| 対象システム/機能 | チャンネル提供者の鍵の移し替え（申し出・取り消し・承認・認めない）、チャンネル提供者へのメール（SQS・通知の Lambda・SES） |
| 関連Skill | feature-implementation-unified |
| 作成日 | 2026-10-04 |
| 作成者 | Claude（開発者との検討） |
| 承認者 | 開発者 |
| ステータス | 実装済 |
| 版 | 1.0 |

## 目的・背景

チャンネル提供者が鍵をなくした・漏れたときに、運営の本人確認を経て新しい鍵に移せるようにする（ADR-001 D-3・A-15、API-001 C-11）。あわせて、判定・取り下げ・移し替えの結果をチャンネル提供者にメールで知らせる（ADR-001 A-19、API-001 C-14）。

## 対応元ID（トレーサビリティ）

| 対応元ID | 内容 | 対応状況 |
|---|---|---|
| ADR-001 | A-15（鍵の移し替え）、A-19（SES・SQS・デッドレターキュー・警報） | 実装（SES で実際に送るのは ADR-001 T-2・T-3 の後） |
| API-001 | 移し替えの 6 操作、C-11、C-14、`transfer_pending`、CV-09、CV-13 | 実装 |
| DM-001 | TRANSFER、チャンネル提供者の鍵の状態、移し替えの承認のトランザクション、DV-08、`notification.sent`・`notification.failed` | 実装（下の J-5・J-6・J-10） |
| platform API-CHANNEL-LIST | P-9、`publisherChange`、V-16 | 実装 |

## 方針・決定事項

| No. | 判断 | 理由 |
|---|---|---|
| J-2 | 申し出は、最初の紐づけと同じ一度きりの文字列への署名で新しい鍵を示し、理由（`lost`/`leaked`/`other`）、散策者に見せる理由（60 文字まで）、運営への説明を付ける。新しい鍵は `pending_transfer`、そのアカウントIDはこの時点で予約する | API-001。認められなくても、そのアカウントIDは再利用させない（DM-001 M-7） |
| J-3 | 本人確認の「鍵とは別の経路」の手順は決めておかず、運営が確かめた方法と内容を記録する（両方必須） | ADR-001 未決事項 No.5 は運用の開始前に決める |
| J-4 | 承認は 1 つのトランザクションで、移し替え・チャンネル提供者（新しいアカウントID、ロックを外す）・新旧の鍵・すべてのチャンネル・古い鍵の審査待ちの申請（`uploading`・`validating` を含む。→ `returned`）・操作の記録を書く。あとでアップロードを `archive/` に移し、公開を頼み、メールを頼む | DM-001。機械審査が後から来ても、`uploading` を条件に書くので記録は変わらない |
| J-5 | `publisherChange` は、承認のときに `from`（リストに載っている版のチャンネル提供者）・`at`・`reason` を書き、新しい鍵で署名した最初の版の承認で `until`（90 日後）を書く。公開の Lambda は、`until` が過ぎておらず、`from` が載せる版のチャンネル提供者と違うときだけ載せる | platform API-CHANNEL-LIST は「移し替え後の最初の版から 90 日」。古い版が載っている間に出すと `from` と `publisher` が同じになり V-16 に反する |
| J-6 | 運営の画面の一覧は、確認待ちを GSI2 `QUEUE#TRANSFER`（古い順）、それ以外を GSI1 `TRANSFERS`（新しい順、状態で絞る）から読む | 過去の申し出と本人確認の記録を見るため（DM-001） |
| J-7 | 退会すると、確認待ちの申し出は取り消しになり、新しい鍵は外れる | DM-001 の退会 |
| J-8 | メールは、状態を変えたトランザクションのあとに SQS に知らせを入れ、通知の Lambda が送る。キューに入れられなくても操作は成功させる（ログに残す） | ADR-001 A-19、API-001 C-14 |
| J-9 | 送る出来事は、承認・差し戻し・却下・取り下げ・移し替えの承認・認めない。本文は結果・理由（指摘、運営のメッセージ）・画面へのリンクだけ。宛先は Cognito で確認済みのメールアドレス（`contact` ではない） | C-14。見本・運営の ID・トークンは入れない |
| J-10 | 同じ知らせが 2 度届いても 1 通にするため、送ったら `NOTICE#{noticeId}`（30 日の TTL）と `notification.sent`（メッセージ ID）を書き、送る前に確かめる | SQS の標準キューは同じメッセージを 2 度届けることがある（CV-13） |
| J-11 | 3 回送れなければ、最後の試みで `notification.failed` を残し、メッセージはデッドレターキューへ。デッドレターキューに入ったら運営の警報（SNS）。確認済みのアドレスがない・退会したチャンネル提供者は、再送せず `notification.failed`（`no_verified_email`） | ADR-001 A-19 |
| J-12 | 送り方は環境の設定 `notify` で選ぶ。開発用は `log`（SES を呼ばず、件名と本文の長さだけをログに出す）。本番も、独自ドメイン（ADR-001 T-2）と SES のサンドボックスの解除（T-3）までは `log`。`ses` にすると、その送信元のドメインの ID と構成セットにだけ `ses:SendEmail` を許す | 開発用は送らずに記録だけにする |
| J-13 | バウンス・苦情を SES の構成セットで受けて操作の記録に残すのは、本番でドメインを用意するとき（ADR-001 T-2・T-3） | 開発用は送らないため |

## 未決事項・リスク

| No. | 内容 | 対応 |
|---|---|---|
| 1 | 本人確認の手順（ADR-001 未決事項 No.5） | 運用の開始前に、運営の手順書で決める |
| 2 | 実際にメールを送るのは、独自ドメイン（ADR-001 T-2）・DKIM/SPF/DMARC・SES のサンドボックスの解除（T-3）・バウンスと苦情の受け取りの後 | 本番の準備で |
| 3 | 移し替えを承認したあと、`publisherChange` が載るのは新しい鍵の版が承認されてから。それまでのアプリは古い版を使い続ける | platform API-CHANNEL-LIST P-9 のとおり。漏れたときは運営が取り下げを検討する（運営の使い方に記載） |
| 4 | 送ったあと記録の書き込みに失敗すると、再送で 2 通になりうる | 起きにくく、害も小さいので受け入れる |
