# DES-014 チャンネルと素材集を画面で作る（下書き）

## 文書情報

| 項目 | 内容 |
|---|---|
| 文書ID | DES-014 |
| ドキュメント種別 | 機能設計書 |
| 対象システム/機能 | SPA（`web/`）: チャンネルと素材集の編集の画面、管理 API（`api/src/console/`）: 下書きの保存・下書きの機械審査・過去の申請の取り出し、機械審査の Lambda（`validator/`）、受付用の S3、データモデル |
| 承認者 | 開発者 |
| ステータス | 承認済（2026-11-04） |
| 版 | 1.0 |

## 目的・背景

今は、チャンネル提供者がパッケージ（`channel.json`・`prompts/`・`resources/`）を、素材提供者が素材集（`collection.json`・`resources/`）を、手元で ZIP にして申請の画面に渡している（[DES-003](DES-003-publisher-console.md) J-10、[DES-010](DES-010-materials-screens.md) N-2）。JSON の項目・文字数・ファイルの置き場所の決まりを手で守るのは難しい（DES-010 未決事項 No.2）。

これを、画面のフォームで作れるようにする。作りかけの内容は**下書き**として管理システムに保存し、どの端末からでも続きを編集できるようにする。できあがったら、今と同じくブラウザで署名して申請する。

## スコープ・非スコープ

スコープ:
- チャンネルの編集: `channel.json` の項目、プロンプトの文章、同梱の素材（`resources`）、きっかけ（`cues`）、素材集の宣言（`collections`）、申請の入力（アイコン・説明・タグ・地域）
- 素材集の編集: `collection.json` の項目、素材（`resources`。題材 `about`・タグを含む）
- 下書きの保存・読み込み・削除（チャンネル・素材集ごとに 1 つ）
- 下書きの始め方: 空から、過去の自分の申請から、手元の ZIP から
- 下書きからの申請（今の申請の API をそのまま使う）
- 下書きのままの機械審査（申請の 1 日の数を使わない）

非スコープ:
- パッケージ・素材集の形式（platform [API-CHANNEL-PACKAGE](https://github.com/duwenji/yorisoi-platform/blob/main/docs/contracts/API-CHANNEL-PACKAGE.md)・[API-MATERIALS](https://github.com/duwenji/yorisoi-platform/blob/main/docs/contracts/API-MATERIALS.md)）は変えない
- 申請・機械審査・運営の審査（DES-003〜DES-005・DES-007）は変えない
- 外部の素材（音声・映像・大きな画像）のファイルを管理システムに置くこと。今と同じく、チャンネル提供者・素材提供者が自分の HTTPS の置き場所に置く
- 複数の人で同じ下書きを編集すること（DM-001 M-1 のとおり 1 アカウント 1 ユーザー）

## 方針・決定事項

### 全体の形

| No. | 判断 | 理由 |
|---|---|---|
| R-1 | **編集と ZIP の組み立てはブラウザで行う**。サーバーは下書きを中身を見ずに預かるだけ。申請は、ブラウザが下書きからパッケージの ZIP を組み立て、今の申請の画面と同じく署名して、今の申請の API（`POST …/submissions` と署名付き POST）で送る | 署名がもともとブラウザの中なので、サーバーに ZIP を作る処理を足さずに済む。機械審査・審査はそのまま使える |
| R-2 | **下書きは署名前の中身だけ**を持つ。`signature.json` は入れない（読み込んだ ZIP にあれば捨てる）。鍵のファイルと合言葉は下書きに入れず、今と同じく申請のときにだけ使う | API-001 C-13。下書きが漏れても署名には使えない |
| R-3 | **下書きの形**: 1 つの ZIP（管理システムの中だけで使う形で、アプリには届かない）。`package/` の下にパッケージ・素材集のファイル（`channel.json` か `collection.json`、`prompts/`、`resources/`）、`draft.json` に申請の入力（チャンネルは説明・タグ・地域・運営への説明、素材集は運営への説明）、チャンネルは `icon.png`。3MB まで | パッケージの 2MB とアイコンの 100KB が入る。1 つにまとめると版（`rev`）も 1 つで済み、保存の途中で一部だけ変わることがない |
| R-4 | **保存は管理 API に ZIP をそのまま送る**（`PUT …/draft`、`application/zip`、`If-Match`）。読み込みも管理 API から ZIP で受け取る。過去の申請のパッケージ・アイコンは、運営の審査と同じく署名付き URL（5 分）で受け取る | 3MB なら API Gateway と Lambda の上限（6MB）に収まり、署名付き POST の 2 段にしなくて済む。`If-Match` で、別のタブの保存を上書きしない（API-001 C-8） |

### 下書き

| No. | 判断 | 理由 |
|---|---|---|
| R-5 | **チャンネル・素材集ごとに下書きは 1 つ**。登録したチャンネル ID・素材集 ID に付く（先に ID を登録する）。上限は数えない（チャンネル 5 つ・素材集 5 つまでなので、1 アカウント 30MB まで）。保存の回数は API Gateway の流量の制限だけで抑える | 上限（DM-001 M-2・M-19）の中に収まる。下書きの数と置き場所の大きさに別の上限が要らない |
| R-6 | 下書きを読み書きできるのは**持ち主だけ**。運営も見ない（API-001 C-12 の例外） | 下書きは申請する前の作りかけで、審査の対象ではない |
| R-7 | **保存できる状態**: アカウントが `active` で、チャンネル・素材集が取り下げられていないこと。停止中（M-10）・取り下げのあとは保存できず（`publisher_not_active`・`invalid_state`）、読み込みと削除だけできる。退会（M-15）では下書きも消す | 停止中は申請もできない。退会のあとに作りかけの中身を残さない |
| R-8 | **残す期間**: 最後の保存から 180 日。過ぎたら消す（DynamoDB の TTL と、S3 のライフサイクル）。申請しても下書きは残し、次の版の編集をそこから続けられる | 長く放っておかれた中身を残さない。保存のたびに新しいキーに書くので（R-12）、S3 のライフサイクルの日数でそのまま消える |

### 画面

| No. | 判断 | 理由 |
|---|---|---|
| R-9 | **入力をその場で確かめる**: 文字数（`name` 20 字、`summary`・`greeting` 60 字、プロンプトのスロットごとの上限と合計 4,000 字、テキストの素材 2,000 字、`alt` 120 字など）、列挙の値、`{{`・URL・見出しの行・CR、ID の書式と重なり、素材とファイルの対応、画像の形式・大きさ（パッケージの中は 300KB・長い辺 1,600px）、パッケージ全体の大きさ（署名の分を見込んで 2MB）、`prefer`・`skip` の重なり、きっかけの数（500 個、題材を問わないもの 5 個）、宣言した素材集・基準がどれかのきっかけで使われていること、見せ方と素材の種類の組み合わせ（[見せ方の一覧](https://github.com/duwenji/yorisoi-platform/blob/main/docs/contracts/API-CHANNEL-PACKAGE.md#見せ方)）。足りない・誤った項目があっても保存はでき、申請のボタンだけを止める。画面で確かめられないもの（素材集の参照の解決・利用許諾・画像の中身・外部の素材のハッシュなど）は、下書きの機械審査（R-16）で確かめる | 機械審査に落ちると 1 日の申請の数（20 回）を使う。作りかけでも保存はしたい |
| R-10 | **列挙の値**（スポットの種類・機能・見せ方・過ごし方・ジャンル・背景音など）は `packages/protocol` に置き、validator のテストで core-format の値と同じかを確かめる | 画面と機械審査で値がずれないように。`FEATURES` はすでに `packages/protocol` にある |
| R-11 | **画面で扱わない項目を落とさない**: 読み込んだ `channel.json`・`collection.json` のうち、フォームにない項目（`selectors`・`shorthands`・`present[].params` など）は「そのほかの項目（JSON）」の欄でそのまま編集でき、保存・申請で元のまま残す | 形式の項目が増えても、画面を直すまで使える。手元の ZIP を読み込んでも中身が欠けない |

画面の構成（チャンネル提供者の画面のチャンネルの詳細と、素材集の詳細に「編集」を足す）:

| 欄 | チャンネル | 素材集 |
|---|---|---|
| 始め方 | 空から（必須の項目に既定の値を入れる）・過去の申請から（承認された版はいつでも。差し戻し・機械審査の不合格などは、受付用の S3 に残っている間（DM-001 M-4 のとおり結果から 90 日まで））・手元の ZIP から。下書きがあるときは「下書きを置き換える」と確かめる | 同じ |
| 基本 | 名前・要約・言語・版（最後に承認した版 + 1 を出す）・過ごし方・ジャンル・必要な機能・あいさつ | 名前・要約・言語・版・利用許諾（チャンネル提供者 `*` か一覧、アプリ、AI の根拠） |
| 話し方 | 話す頻度・6 つの出来事・スポットの好み（優先・話題にしない）・解説の長さ・雰囲気・背景音 | — |
| プロンプト | スロットごとの文章の欄（文字数と合計を出す。空なら標準の文章を使うと添える） | — |
| 素材 | テキスト（本文の欄）・画像（ファイルを選ぶ。`alt`・`credit`）・外部の素材（URL・`mime`・`size`・`sha256`・`durationSec`・書き起こし・`credit`）。外部の素材は、置き場所に上げる前の手元のファイルを選べば、`size`・`sha256`（音声・映像は `durationSec` も）をブラウザの中で計算して入れる（ファイルは送らない）。手で入れることもできる | 同じに加えて、題材（スポットの OSM の ID と名前、地点。位置は地図で選ぶ）・タグ |
| きっかけ | 一覧と編集。題材（スポット・題材を問わないスポット・地点・出来事）、語り（`replace`・`add`）、繰り返し、見せ方と素材（同梱の素材を選ぶか、素材提供者への参照の候補を 1〜3 個並べる）。地点は地図で選ぶ | — |
| 素材集 | 使う素材集の宣言（別名・ID・最低の版） | — |
| そのほか | そのほかの項目（JSON）（R-11） | 同じ |
| 確かめる | 「機械審査にかける」（保存した下書きを確かめる。R-16）と結果。保存したあとに変えた分は確かめていないことを示す | 同じ |
| 申請 | アイコン（PNG、256×256 以下、100KB 以下）・説明・タグ・地域・運営への説明 → 「AI の一次審査」 → 鍵のファイルと合言葉 →「署名して申請する」 | 運営への説明 →「AI の一次審査」→ 鍵 →「署名して申請する」 |

### 実装上の判断

| No. | 判断 | 理由 |
|---|---|---|
| R-12 | 保存は、受付用の S3 の新しいキー（`drafts/ch/{channelId}/{draftId}.zip`、`drafts/col/{collectionId}/{draftId}.zip`。`draftId` は ULID）に書いてから、下書きの項目を `rev` を条件に書き換え、前のキーを消す。条件で落ちたら、書いた新しいキーを消して 412 `precondition_failed` | S3 と DynamoDB を 1 つのトランザクションにできないので、項目が指すキーが必ず中身のある 1 つになるようにする |
| R-13 | サーバーが確かめるのは、大きさ（3MB）と ZIP であること（先頭のバイト）だけ。中身は開かない | 中身の判定は申請の機械審査に任せる（R-1） |
| R-14 | 下書きの保存・削除は、操作の記録（ARCH-001 A-16）に残さない。下書きから作った申請は、今と同じく申請として残る | 申請する前の作業で、審査と公開に関わらない。保存のたびに記録が増えるのを避ける |
| R-15 | 受付用の S3 と公開用のバケットの CORS に `GET` を足し、画面の CSP の接続先・画像に公開用のバケットを足す（過去の申請の署名付き URL を画面が読むため）。地図のタイル（地理院）は画像に常に許す | 今は署名付き POST だけを許している。`GET` も署名付き URL がなければ読めない。公開用のバケットのものはもともと CloudFront で公開している |

### 下書きの機械審査

| No. | 判断 | 理由 |
|---|---|---|
| R-16 | **保存した下書きを、申請と同じ機械審査にかけられる**（`POST …/draft/check`）。確かめるのは申請の機械審査と同じ手順（core-format の確認、ID・アカウント・版、素材集の参照の解決と利用許諾、アイコン、素材集の外部の素材の大きさと SHA-256、公開中のチャンネルが使っている素材（D-8））。申請の 1 日の数（20 回）は使わない | 機械審査に落ちて申請の数を使うのを避ける（R-9 の画面の確かめで足りないところを補う） |
| R-17 | **署名は確かめない**: 下書きには署名がないので、機械審査の Lambda が、アカウントの今の鍵（DM-001 KEY の `publicKey`）を `publisherKey` に入れた `signature.json` を作り（ファイルの SHA-256 の一覧は下書きから計算し、`sig` は空）、署名をそのまま通す検証器で core-format にかける。これで、`publisher` がアカウントIDと合うか（`publisher_mismatch`）を含めて、署名の他は申請と同じ判定になる。core-format は変えない | 秘密鍵をサーバーに送らず（API-001 C-13）、鍵のファイルを確かめるたびに開かなくて済む。申請のときには、本当の署名を今と同じく確かめる |
| R-18 | **非同期で動かす**: 管理 API は下書きの項目に `check`（`state`: `running`、確かめる下書きの `rev`）を書き、機械審査の Lambda を非同期で呼んで 202 を返す。Lambda は結果を `check`（`state`: `done`、`validation`）に書く。画面は下書きの要約を読み直して結果を出す。結果の `rev` が今の下書きの `rev` と違えば、画面は「保存したあとに変えた分は確かめていない」と出す | 素材集の外部の素材の確認は最長 10 分かかり（DES-007 J-5）、API Gateway の 30 秒に収まらない |
| R-19 | **上限**: 下書きの機械審査は 1 アカウント 1 日 50 回（日本時間。チャンネルと素材集で合わせて数える。DM-001 QUOTA の `draftChecks`）。1 つの下書きで同時に 1 つだけ（`running` の間は 409 `invalid_state`）。15 分たっても `running` のままなら、次の要求で新しく始められる | 外部の素材を読みに行くので、回数を抑える。Lambda が途中で止まっても塞がらないように |
| R-20 | 結果は `Validation`（API-001 C-19 と同じ形）で返す。見本用のプロンプトは作らない。下書きにアイコンがなければ、アイコンの確認だけ飛ばして `warnings` に `icon_missing` を入れる。結果は操作の記録に残さない（R-14 と同じ） | 画面の表示を申請の結果と共通にできる。見本は運営の審査のためのもの |

## API（API-001 に足すもの）

| メソッド | パス | 権限 | 概要 |
|---|---|---|---|
| GET | `/api/channels/{channelId}/draft` | P（持ち主だけ） | 下書きの ZIP（`application/zip`）。`ETag` に `rev`。ないときは 404 `not_found` |
| PUT | `/api/channels/{channelId}/draft` | P（持ち主だけ） | 下書きを保存する。本文は ZIP。初めての保存は `If-None-Match: *`、2 回目からは `If-Match`。応答は下書きの要約（`rev`・`updatedAt`・`size`・`expiresAt`） |
| DELETE | `/api/channels/{channelId}/draft` | P（持ち主だけ） | 下書きを消す（`If-Match`） |
| POST | `/api/channels/{channelId}/draft/check` | P（持ち主だけ） | 保存した下書きを機械審査にかける（`If-Match` に確かめる下書きの `rev`）。202 と下書きの要約（R-18）。上限は 429 `quota_exceeded` |
| GET | `/api/channels/{channelId}/submissions/{submissionId}/package` | P（自分のもの） | 申請のパッケージとアイコンの署名付き URL（5 分）。運営の `GET /api/admin/…/package` と同じ形。受付用の S3 から消えていれば、承認された版は公開用のバケットのもの（`pkg/`・`icons/`・`col/`）を返し、そうでなければ 404 `not_found`（`detail` に消えたこと） |
| GET・PUT・DELETE | `/api/collections/{collectionId}/draft` | 素材提供者（持ち主だけ） | 素材集の下書き（チャンネルと同じ） |
| POST | `/api/collections/{collectionId}/draft/check` | 素材提供者（持ち主だけ） | 素材集の下書きを機械審査にかける（チャンネルと同じ） |
| GET | `/api/collections/{collectionId}/submissions/{submissionId}/package` | 素材提供者（自分のもの） | 素材集の申請のパッケージの署名付き URL |

- チャンネル・素材集の応答（`GET /api/channels/{channelId}` など）に、下書きの要約 `draft`（`rev`・`updatedAt`・`expiresAt`・`check`）を足す（持ち主だけに返す）。`check` は `state`（`running`・`done`）・`rev`（確かめた下書きの版）・`startedAt`・`checkedAt`・`validation`
- エラーは API-001 のエラー表のもの: 3MB を超える（413 `payload_too_large`）、ZIP でない（400 `invalid_request`）、`rev` が違う（412 `precondition_failed`）、`If-Match` も `If-None-Match` もない（428 `precondition_required`）、停止中（403 `publisher_not_active`）、取り下げのあと（409 `invalid_state`）。新しいコードは足さない

## データモデル（DM-001 に足すもの）

| 種類 | PK | SK | 属性 |
|---|---|---|---|
| チャンネルの下書き | `CH#{channelId}` | `DRAFT` | `key`（S3 のキー）、`size`、`sha256`、`rev`、`createdAt`、`updatedAt`、`ttl`（最後の保存から 180 日）、`check`（R-18） |
| 素材集の下書き | `COL#{collectionId}` | `DRAFT` | 同じ |

| バケット | キー | 保持 |
|---|---|---|
| 受付用（非公開） | `drafts/ch/{channelId}/{draftId}.zip`、`drafts/col/{collectionId}/{draftId}.zip` | 最後の保存から 180 日で消す（ライフサイクル。R-8）。新しく保存したら前のキーを消す（R-12） |

- 退会のトランザクション（DM-001「DDL方針」）に、チャンネル・素材集の下書きの項目の削除を足す。S3 のキーは、トランザクションのあとに消す（消し損ねても 180 日で消える）
- 持ち主は、チャンネル・素材集の項目の `publisherId` で確かめる（下書きの項目には持たない）
- 1 日の数（`PUB#{publisherId}` / `QUOTA#{yyyy-mm-dd}`）に `draftChecks` を足す（R-19）
- 機械審査の Lambda は、`drafts/` を読めるようにし、下書きの項目の `check` を書けるようにする

## 確認観点

| No. | 観点 |
|---|---|
| RV-01 | 空から作ったチャンネル・素材集の下書きを、画面の入力だけで機械審査に合格させられる（素材・きっかけ・素材集の宣言を含む） |
| RV-02 | 過去の申請・手元の ZIP から読み込み、何も変えずに申請すると、署名を除いて同じファイルのパッケージになる。画面にない項目も残る（R-11） |
| RV-03 | 2 つのタブで同じ下書きを保存すると、後の保存が 412 になり、先の保存の中身が残る（R-4・R-12） |
| RV-04 | 別のアカウント・運営は、下書きを読めない（404）（R-6） |
| RV-05 | 停止中のアカウント・取り下げたチャンネルの下書きは、読めて消せるが保存できない。退会で下書きが消える（R-7） |
| RV-06 | 画面の入力の確かめ（R-9）で申請のボタンが止まる項目は、機械審査でも不合格になる（同じ見本の誤りのパッケージで比べる） |
| RV-07 | `packages/protocol` の列挙の値が core-format の値と同じ（R-10。validator のテスト） |
| RV-08 | 下書きに `signature.json`・鍵のファイル・合言葉が入らない（R-2） |
| RV-09 | 下書きの機械審査の結果が、同じ中身を署名して申請したときの機械審査の結果と同じになる（署名の誤りを除く。R-16・R-17） |
| RV-10 | 下書きの機械審査は申請の 1 日の数を使わず、1 日 50 回で止まる。`running` の間の 2 つ目は 409、15 分を過ぎれば始め直せる（R-19） |

## 未決事項・リスク

| No. | 内容 | 対応 |
|---|---|---|
| 2 | 画面は CSP で接続先を限っているので（ARCH-001 A-14）、外部の素材を置き場所から取って `size`・`sha256` を確かめられない | 手元のファイルから計算する欄と手で入れる欄を置き、計算の仕方（`sha256sum` など）を利用ガイドに書く。置き場所の中身と合うかは、素材集では下書きの機械審査（R-16）で確かめる。チャンネルの外部の素材は、申請の機械審査でも読みに行かない（今と同じ） |
| 3 | きっかけを 500 個まで作れるが、画面で 1 つずつ作るのは手間がかかる | 一覧の絞り込みと複製を付ける。それでも足りなければ、表（CSV）からの取り込みを考える |
