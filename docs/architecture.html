チャンネル管理システムの構成図

SanpoGuide のアプリに第三者のチャンネルと素材集を届けるため、チャンネル提供者・素材提供者の申請を審査し、承認したものだけを署名したリストで公開するシステムです。5 枚の図で説明します。図 1 で「誰が何を使い、どこに何があるか」をつかみ、図 2〜5 で申請の一生・信頼の鎖・公開の処理・メールと警報を追います。

アプリとの境界は platform の API-CHANNEL-LIST（承認済みチャンネル・リスト）だけです。アプリはこのシステムの API を呼ばず、公開された静的ファイルを取りに来ます。図はコードと CDK から手で書き起こしたもの（2026-10-12 時点。素材集と素材提供者は 2026-10-11 に追加）です。Lambda・バケット・申請の状態を足したり変えたりしたときは、この文書と docs/architecture.md も更新してください。

図 1 · 全体

公開の面に書くのは「公開の Lambda」だけ

運営・チャンネル提供者・素材提供者が使う 管理の面（ログインが要る画面と API）と、アプリが取りに来る 公開の面（誰でも読める静的ファイル）は、DynamoDB と公開の Lambda でしかつながっていません。管理の面に何かあっても、公開されるのは公開の Lambda が署名したリストだけです。

図 2 · 申請の一生

チャンネルごとに「決着していない申請」は 1 つだけ

申請はアップロード待ちから始まり、機械審査と運営の審査を経て、承認か、どこかの出口で終わります。決着していない間はチャンネルの pendingSubmissionId がその申請を指し、次の申請を受け付けません。出口に出たらチャンネルが空き、ファイルは archive/ に移って 90 日で消えます。

図 3 · 信頼の鎖

アプリが最初から知っているのは、リストID（ルート鍵の指紋）だけ

アプリは散策者が登録したリストID から始めて、署名とハッシュを 1 段ずつたどります。どの段で合わなくても、その文書は捨てて前のものを使い続けます。鍵は 3 か所に分かれていて、どれもリポジトリと管理 API の外にあります。

図 4 · 公開の処理

何度呼ばれても、リストは 1 つずつ順番に作る

6 つのきっかけはすべて同じ公開の Lambda を呼びます。同時実行を 1 に絞り、公開の記録の先頭を seq を条件に書き換えるので、2 つの公開が重なっても seq は飛ばず、戻りません。内容が変わらなくても毎日作り直すのは、リストの期限が 14 日だからです。

図 5 · メールと警報

メールが届かなくても、操作は失敗にしない

判定・取り下げ・移し替えの結果（素材集の更新・利用許諾の縮小・取り下げは、使っているチャンネル提供者にも）は、状態を書いたあとで SQS に知らせを入れ、通知の Lambda がチャンネル提供者・素材提供者に送ります。公開の Lambda も、外部の素材の不具合を同じキューに入れます。キューに入れられない・送れないときも、操作そのものは成功のままです。

素材集と素材提供者（DM-001 1.3）

素材集は、チャンネルと同じ仕組みに乗る別の単位

素材集は、チャンネルが参照する文字・画像などの素材のまとまりです（platform の ADR-MATERIAL-PRODUCERS・API-MATERIAL-PRODUCER）。素材提供者が自分の鍵で署名して申請し、運営がチャンネルとは別に審査・承認して、同じリストの collections[] に載せます。申請の状態の移り方（図 2）・信頼の鎖（図 3）・公開の処理（図 4）・メール（図 5）は、チャンネルと同じ仕組みを使います。違いだけをまとめます。

どこに何があるか
